# Request logging guarantees (the middleware contract)

Both `RequestLoggingMiddleware` adapters (`collide_logging.django`, `collide_logging.starlette`) hold the same contract. Know it before touching either — the edge cases below are deliberate, not bugs to "fix."

- **One `http.request` line per HTTP request.** It is emitted at `error` when `outcome` is `error`, otherwise `warning` for 4xx and `info` below 400. It always carries `request_id` (always server-generated, 16 hex characters; an inbound `X-Request-ID` is never adopted), plus `client_request_id` when the inbound header is well-formed (`[A-Za-z0-9._-]{1,64}`), `method`, `path`, `status`, and `duration_ms`. The Django line also carries `user_id` (`str(request.user.pk)` for an authenticated user; omitted otherwise, and never `user`); the Starlette/ASGI adapter does not log a user.
- **Each request is a unit of work** (`open_unit`/`close_unit` in `_unit.py`), opened after the ids are bound and closed in the same `finally`, so a unit never leaks into the next request. `open_unit()` returns `(unit, token)`, so the adapter holds the unit directly. `close_unit` marks the unit closed and drops its annotations and exception; `current_unit()` returns `None` for a closed unit, so copies of the request's context that outlive it (`asyncio.create_task` children, `run_in_context` threads) see no unit and `annotate()`/`record_exception()` do nothing there. `close_unit` suppresses a token from another context, and the id reset sits in an inner `finally`, so it runs even if closing the unit fails. The line is written by `emit_outcome()` in `_unit.py`, which owns the field merge order, `duration_ms` (from `unit.start`) and the level rule for every adapter. It carries:
  - `outcome`: `error` when an exception was recorded on the unit or the status is 500 or more, otherwise `ok`;
  - the unit's `annotate()` fields, applied first so the line's own fields (`method`, `path`, `status`, `duration_ms`, `user_id`, ids) always win; `clean_fields` already drops library-owned names;
  - after a recorded exception: `error_type` (the bare class name) and `exc_info=unit.exc`, so `_render_exception` adds `exception_type` (the qualified class name), the frames, the built-in attributes, the declared fields and the captured `log_context` fields. A capture stamped by another unit is ignored while a unit is open, so an exception re-raised here without a block carries none of an earlier request's context.
- **Django view exceptions never reach the middleware**: Django converts them to a 500 response inside `get_response`. A `got_request_exception` receiver (`dispatch_uid`, `weak=False`, never raises) records `sys.exc_info()[1]` on the current unit. Under ASGI the conversion runs in an asgiref thread with a copied context; the unit is a mutable object reached through the ContextVar, so the record lands on the request's unit.
- **No second line for the same failure (Django and uvicorn).** `record_exception()` marks the exception it records (a guarded `setattr`) as carried by an outcome line; the mark outlives the unit. `RecordedExceptionFilter` (core, framework-free, in `_unit.py`) sits on the library's `CollideStreamHandler`, attached by `configure()` so reconfiguring keeps it. It skips a `django.request` or `uvicorn.error` record whose `exc_info[1]` carries the mark: Django logs `django.request` before the middleware sees the 500 response, and uvicorn logs `Exception in ASGI application` after the Starlette middleware re-raises and the unit has closed, so the rule cannot depend on the unit being open. It is a handler filter, not a logger filter, so every other handler of those loggers (`mail_admins`, error reporters) still receives the record. Every other record (a 5xx returned by a view, 4xx warnings, uvicorn startup lines, a different exception) passes. The middleware's `__init__` connects only the receiver (idempotent by `dispatch_uid`).
- **Exception path (both adapters, #41 Django / #44 Starlette).** When the wrapped handler/app raises an unhandled exception, the middleware records it on the unit and emits a status-500 line with `outcome="error"` at `error` level carrying the traceback (`exc_info`) before re-raising. No response exists on that path, so the `X-Request-ID` response header is **not** set and the status is reported as **500 even if the response start already fired** — the request failed, and that is the truthful signal. `request_id` still appears because it rides the bound contextvar (reset happens in a `finally`, after the emit).
- **`request_id` and `client_request_id` never leak past a request.** They are bound on entry and reset in a `finally`, on every path including the exception path.
- **Django streaming responses defer the line until stream close** (`response.close()`), so `duration_ms` reflects time-to-close rather than time-to-first-byte, and abandonment still logs. The unit is snapshotted (`snapshot()` in `_unit.py`) when the response is returned; an `annotate()` inside the streaming body does nothing, since the unit has closed. Known limit until a stream wrapper lands: a body that fails mid-stream still logs `outcome="ok"` with the status the view returned. This deferral is Django-only — pure-ASGI (`starlette.py`) has no streaming special case because `await self.app(...)` returns only after the body drains, so its `duration_ms` is already correct.
- **One known un-loggable case — Django ASGI client-disconnect mid-stream (#42, open).** On an ASGI `StreamingHttpResponse` whose client disconnects before the body completes, Django's `ASGIHandler` cancels the request task and sends `request_finished` **without** calling `response.close()`, so the deferred line never fires and that one request does not log. Every other termination (WSGI anything, all non-streaming, ASGI streaming that completes or errors) logs. This is not currently fixable from a standard `MIDDLEWARE` entry — see #42 before attempting it, and do not assume the Starlette adapter shares it (it does not: pure-ASGI drains before the `await` returns).
